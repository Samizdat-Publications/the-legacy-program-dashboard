# Both drawers, both directions, on the same curve

**27 August 2026.** Stewart, from the live site: *"I can drag the right sidebar but what I
want is the sidebar to have a clickable edge that, when clicked, on a curved motion sends
the drawer back to its closed position on the right, same with the left pane, then I should
be able to open the closed drawer by clicking it to expand."*

**Half of this already existed and he had not seen it.** The dossier's tab and its slide
landed in PR #6 on the morning of the 27th and were never deployed, so the board he was
describing is the one from the 26th. The genuinely missing half was the left rail, which
had nothing: no edge affordance in either direction, and a fold that was not a fold.

---

## 1. The rail was `display:none`

```css
#app.rail-off .rail{display:none}
#app.rail-off .body{grid-template-columns:minmax(0,1fr) var(--dock-w)}
```

Two separate reasons that could never have animated:

- **`display` is not interpolable.** No duration and no easing rescues it. This is the
  third instance of the family error in this shell — `.dock{transition:width}` on a grid
  child, then the analyst's `display:none` fold, now this.
- **The rail TRACK was removed entirely.** The grid went three columns to two in one step,
  so even a width animation would have had nothing to run against.

The fix is the dock's, applied unchanged: the track always exists, the width is a
**registered** length so it has a type and can interpolate, and the collapsed state is a
30px spine carrying its own label rather than an absence.

```css
@property --rail-w { syntax:'<length>'; inherits:true; initial-value:202px; }
#app{transition:--rail-w 320ms cubic-bezier(.22,1,.36,1)}
#app.rail-off{--rail-w:30px}
```

Sampled every frame, both directions: **202px to 30px over 11-12 distinct widths**, and
**2 distinct widths with the transition killed.** That gap is the whole assertion — a
discrete flip must not be able to pass a check written to detect a slide.

## 2. The tab, in both directions

`.rail-fold` is `.dock-fold` mirrored across the window: fixed, pinned to
`calc(var(--rail-w) - 1px)`, transitioning `left` on the panel's own curve so the tab rides
the edge instead of teleporting to meet it. Fixed rather than absolute for the same reason
the dock's is — a child hanging off the pane's edge gets clipped by its own `overflow`.

The collapsed spine is one big click target and names itself in CSS, so the reader never
has to find an 11px chevron: `FILTERS — CLICK TO OPEN`, matching `DOSSIER — CLICK TO OPEN`.

## 3. What the check caught on its first run

`foldPanels()` — which **FIT ALL and every entry path call** — folded the rail by setting
the class and the flag by hand and never told `applyChrome`. So the rail shut while its
`CLICK TO CLOSE` tab stayed on screen pointing at an already-closed pane, and the toolbar
button went on saying `◀ Rail`.

Nothing in the source said so. The check said so, by measuring **one** distinct width on a
fold: the pane it had been told to close was closed already. `foldPanels` now goes through
`applyChrome`, which is the single owner of that chrome.

Verified through the real button rather than through the passing check, because the check
now normalises the rail open before measuring and would pass either way:

```
rail open                  {"railOff":false,"railW":202,"foldTab":true, "btn":"◀ Rail"}
after FIT ALL (foldPanels) {"railOff":true, "railW":30, "foldTab":false,"btn":"▶ Rail"}
```

## 4. One thing the test had to be told twice

`railSweep` first drove the rail by setting `S.railOpen` and calling `applyChrome()` from
`page.evaluate`. Both are **module-private** — the board is wrapped in an IIFE, which is the
constraint `runtime_check.js` is built around and which this file's author forgot. The
reach silently no-ops, so the assertion measured a rail nothing had ever opened, and
reported `false/false/false` rather than an error. It clicks `#railbtn` now.
